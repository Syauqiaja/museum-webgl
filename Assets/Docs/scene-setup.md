# Scene Setup

What each scene must contain to behave correctly, which editor generators build parts of it,
and what is currently unwired after the 2026-08-19 recovery. Read this when a scene "does
nothing" — in this project that is usually an empty serialized field, not a bug in a script.

## Why so much is unwired

The project was rebuilt from Claude Code transcripts (source files) plus an AssetRipper pass
over the deployed WebGL build (scenes, meshes, materials). AssetRipper Free cannot decompile
IL2CPP wasm, so **every custom MonoBehaviour's inspector values came back empty**. Scripts
and GameObjects exist; the references between them mostly do not. Scenes rebuilt afterwards
by the editor generators (Egrang) are wired; scenes that were only ripped (Dakon, Museum,
Lobby) are not.

## Bootstrap

Three components on one `DontDestroyOnLoad` GameObject: `SessionData`,
`ColyseusNetManager`, `SceneLoader`. Present in **MainMenu** and **Lobby**; **Museum** has
`SceneLoader` only; **Dakon** and **Egrang** have none.

That is correct for the normal path — the bootstrap travels from MainMenu — but it decides
what happens when a scene is opened **directly** in the Editor:

| Opened directly | Result |
|---|---|
| Museum | Walks fine; a doorway press throws on `SceneLoader.Instance` only if the loader is missing |
| Lobby | Its own bootstrap runs; no name set → the name panel appears (its documented fallback) |
| Dakon | No `SessionData` → no seat → offline hotseat. Both exits fall back to `SceneManager.LoadScene` when there is no `SceneLoader`, so they still reach the museum |
| Egrang | Same: offline race in lane 1 |

`ColyseusNetManager` needs a `ServerConfig`; if the field is empty it loads
`Resources/ServerConfig`, so a generated scene does not have to remember it.

## MainMenu

- Bootstrap object.
- **`Platform Panel`** — the `Kamu main pakai apa?` picker shown first, with the
  `HP / Layar Sentuh` and `Komputer` buttons wired to `MainMenu.ChooseTouch` /
  `MainMenu.ChooseDesktop`. Generated by `Museum/Rebuild UI/Main Menu`
  (`MainMenuUIBuilder`), which refuses to run if the scene has unsaved changes. See
  [input-and-platform.md](input-and-platform.md).
- Name input (TMP) + Play button wired to `MainMenu.GoToMuseum`.
- The Play button should stay **disabled until the typed name passes `PlayerNameRules`**
  (2–16 chars after trimming and whitespace collapse) — that guard is what stops anyone
  reaching a room unnamed. `MainMenu.cs` itself only holds `GoToMuseum`; the validation
  wiring lives in the scene.
- `SceneLoader` needs its `loadingScreenPrefab` assigned or every load logs an error and no
  scene change happens.

## Museum

- `SceneLoader` (bootstrap arrives from MainMenu).
- Player rig: `FPSController` (Rigidbody + Collider, `groundMask` set, camera parented under
  the player) driven by `FPSInputReader` with `Assets/Scripts/Player/FPSInput.inputactions`
  — action map `Player`, actions `Move`, `Look`, `Sprint`, `Jump`. Tag the player `Player`,
  or no trigger in the scene fires.
- **Doorways** — one `SceneTriggerPrompt` per game, each needing:

  | Field | Dakon | Egrang |
  |---|---|---|
  | `useLobby` | ✔ | ✔ |
  | `roomName` | `dakon` | `egrang` |
  | `maxPlayers` | 2 | 3 |
  | `displayName` | `Dakon` | `Egrang` |
  | `sceneName` | `Dakon` | `Egrang` |
  | `promptUI` | the "press Enter" panel | same or its own |

  With `useLobby` on the doorway does **not** load the game: it parks a `LobbyRequest` and
  loads `Lobby`. `sceneName` is still the game — the lobby is a stop on the way.
  Both doorways share the root `Canvas/Enter` prompt panel today, so keep their trigger
  volumes apart or give each its own prompt object. The Egrang doorway sits beside the Dakon
  one as a placeholder and still needs moving to its real spot.

- **Exhibit placement** — on 2026-09-09 two pairs of exhibits traded places by a rigid
  transform (yaw + translation about each group's renderer-bounds centre): **Egrang ↔
  Bekelan** and **Engklek ↔ Cirak**. Egrang and Engklek now sit on LT1, Bekelan and Cirak on
  LT2, and each exhibit's props, `Vid` screen, lesson panel, generated lantern light and (for
  Egrang) its `SceneTriggerPrompt` moved together. The four `Vid` screens were reparented to
  the `Vid LT*` group matching their new floor. The swap was rigid, not refitted: Egrang's
  props are 14.3 m deep in an alcove that was 7.9 m, so that room still needs a visual pass.

- **Video screens** — each screen is a `StreamedVideoScreen` (with a `VideoPlayer`) plus a
  `VideoTriggerPlayer` on a trigger collider, and a `RawImage` on a world-space canvas. The
  screen carries a **catalog key**, never a URL. `Museum/Video/Report Video Assignments`
  prints what every screen is currently pointed at.
- **Lesson panels** — one per game, all eighteen, under a scene-root `Lessons (Generated)`
  container: a world-space `LessonPanel` canvas on the wall beside that game's exhibit screen,
  plus a `LessonReader` **on the screen's existing `VideoTriggerPlayer` volume** — the lessons
  add no collider and no new geometry. For Dakon that volume is also the `Dakon Doorway`, so
  one trigger drives the doorway, the video and the panel. Built by
  **`Museum/Rebuild UI/Lesson Panels`**, which also writes the `GameLessonData` assets under
  `Assets/Resources/lessons` and adds the `Q E — Ganti halaman` row to the HUD's KONTROL card.
  Panel *placement* is authored by hand and adopted on rebuild; only the contents regenerate.
  Do not parent a panel to an exhibit prop: those meshes are scaled non-uniformly and would
  shear the canvas. Needs the player tagged `Player`. Paging is keyboard-only (`Q`/`E`) — the
  museum locks the cursor, so nothing on that canvas can be clicked and it deliberately carries
  no `GraphicRaycaster`. See [lessons.md](lessons.md).
- **`Touch Controls`** — the joystick, look area, Lompat, Interaksi and ‹ › overlay, under a
  `TouchOnly` root so it only activates when `SessionData.IsTouch` is true. Generated by
  `Museum/Rebuild UI/Touch Controls` (`TouchControlsUIBuilder`), which also refuses to run
  over an unsaved scene. See [input-and-platform.md](input-and-platform.md).
- Minimap markers use `MinimapOnlyObject`, which needs a `MinimapOnly` layer to exist, the
  main camera to exclude it and the minimap camera to include only it.
- **Lighting** — 71 realtime lights (a sun, 29 lantern point lights, 42 zone fill lights) plus
  25 box-projected reflection probes, the ambient gradient and fog. Do not hand-place them:
  rebuild with **`Museum → Lighting → Build`** (`MuseumLightingBuilder`), which is idempotent
  and keeps everything it makes under a `Lighting (Generated)` root. Then run
  **`Museum → Lighting → Bake Reflection Probes`** — until that runs the probes fall back to
  the skybox. There is no lightmap and no GI: neither is possible on WebGL2 here.
  See [lighting.md](lighting.md) for the values and why.

## Lobby

One generic scene; the game it fronts comes from `LobbyRequest.Pending`. Rebuild it with
**`Museum → Build Lobby Scene`** (`LobbyUIBuilder`) rather than by hand — that generator is a
*total* generator: it rebuilds the scene from empty, styles everything through
`MuseumUIStyle`, wires every controller field and re-saves the seat prefab. Running it is how
the scene was repaired after the recovery.

`LobbyController` needs: `namePanel`, `entryPanel`, `roomPanel`, `nameInput`, `titleText`,
`codeInput`, `codeText`, `slotContainer`, `slotPrefab` (a `LobbySlotView`), `startButton`,
`toastRoot`, `toastText`. Buttons are wired **by method name** —`ConfirmName`, `CreateRoom`,
`JoinRoom`, `StartGame`, `LeaveRoom`, `CopyCode`, `BackToMainMenu` — so those names are
load-bearing; do not rename them without re-wiring the scene.

`useFakeService` must be **off** for a real build, and now is — in `Lobby.unity` and as the
field's default, because `LobbyUIBuilder` adds the controller fresh and never writes the flag,
so a `true` default meant regenerating the scene silently reinstated the fake. Left on, the
controller logs a warning in a player build ("nobody can actually play together") and every
room is in-memory — two browsers can never meet.

The fallback request fields (`fallbackRoomName` = `egrang`, 3 seats, `Egrang`) apply only
when the scene is opened directly with no `LobbyRequest.Pending`.

## Dakon

Needs, on `DakonView`:

- `holeAnchors[20]` — ring order 0–19, indices 0–9 the near side (seat 0), 10–19 the far
  side. `holeLabels[20]` optional.
- `highlightMarker` — moved onto `nextHoleIndex`.
- `handContainer` + `cardPrefab` (a `DakonCard`), `handRoot`, `waitingForTurnPanel`,
  `waitingForTurnLabel`.
- HUD: `turnLabel`, `poolLabel`, `scoreP0Label`, `scoreP1Label`, `toastLabel`,
  `gameOverPanel`, `gameOverLabel`, `gameOverExitButton`.
- `toastLabel` is the `Toast` object at the canvas root — a frame plus a stretched TMP child,
  raised past the modals so a refusal is not hidden behind the panel it refers to. Unassigned,
  every rejection is silent; the view is null-safe, so it fails quietly rather than loudly.
- `gameOverExitButton` is `Game Over/Exit`, held as a **serialized reference** and subscribed
  at runtime — unlike the pause panel's exit, it is not a by-name UnityEvent.
- `storeAnchors[4]` — index = `player * 2 + category`: 0 P1-Monocot, 1 P1-Dicot,
  2 P2-Monocot, 3 P2-Dicot. An unwired bin leaves its seeds in their holes at game over
  rather than throwing.
- **A `MeshCollider` on `dakon_board`** — non-convex, the board's own 41k-triangle mesh, so
  the modelled holes are real cavities. Without it seeds fall past the board entirely. The
  bowls it provides were measured, and those measurements are the view's defaults: a playing
  hole is ~0.06 across with its floor 0.058 below the anchor; a storehouse bin is ~0.09 with
  its floor 0.082 down. Re-measure and update `holeBowlRadius` / `holeBowlDepth` /
  `storeBowlRadius` / `storeBowlDepth` if the board model is ever replaced.
- `pileRadius` is **not** the bowl. It is the fallback layout for a seed that had to be placed
  by hand, and it must stay well inside `holeBowlRadius` — it was 0.15 against a 0.06 bowl
  once, which put "piled" seeds on the tabletop.
- `seedTypes[]` — the eight `SeedType` assets. Empty means the model falls back to the
  string ids `monocot` / `dicot`, cards show a category name and no art, and **the client's
  species ids stop matching the server's**.
- `boardCamera` — used to project a played card's screen position into world space.
- `vignette` — the `Vignette` overlay at the canvas root (a full-screen `Image` plus
  `DakonVignette`), pulsed green when a dropped seed matched its hole and red when it did not.
  The view falls back to `GetComponentInChildren<DakonVignette>` when the field is empty, so a
  scene whose links did not survive still shows the feedback. Its sprite is **baked at runtime**
  by `VignetteTexture` — leave `Image.sprite` empty; an authored sprite is used instead of the
  bake. Right-or-wrong is read off the board (`HoleTypeAt(hole) == drop.Category`), not off a
  wire field: the server sends no such flag and inventing one would split the two repos'
  protocols. It is deliberately **faint and edge-bound** — `peakAlpha` 0.16, and the baked ramp
  starts at 0.72 of the half-width (`VignetteTexture.DefaultInnerRadius`). At the original 0.35
  and 0.45 the tint carried across the board and the hand, which read as a full-screen flash
  over the very thing the player is watching; a vignette has to be legible without being looked
  at. The bake is 256px because a band that narrow banded at 128.

Plus a `DakonNetBootstrap` component in the scene (present, named `Dakon Net Bootstrap`) so
an arriving player reconnects instead of starting a hotseat game.

All of the above is written by `Museum/Rebuild UI/Dakon`
(`Assets/Scripts/Games/Dakon/Editor/DakonUIBuilder.cs`), which also owns the screen's layout:
chip and dialog rects, the padding inside them, the card size, and the hand strip. Re-running
it is safe. Three shapes there are worth knowing before editing the scene by hand:

- **The hand scrolls.** A hand is fifteen cards, which cannot fit across 800 design units at a
  readable size. `HandTransform (1)` is a `ScrollRect`, `Mask` is its viewport, and the inner
  `HandTransform` is the content: fixed-size cards (a `LayoutElement` on `Card.prefab`), a
  `HorizontalLayoutGroup` that controls but does not *expand* them, and a `ContentSizeFitter`
  on the horizontal axis only. Force-expanding instead is what produced a row of clipped
  slivers. A layout group on the viewport fights the fitter — the viewport has none.
- **Seeds are thrown, not tweened.** `DakonSeedBody` gives each spawned seed a rigidbody and
  a collider sized from its own mesh, and `Assets/Settings/DakonSeed.physicsMaterial` gives it
  no bounce and high friction. The eight species prefabs stay pure art — nothing physical is
  authored on them, so there is no per-prefab setup to keep in step. A seed is thrown **once**: the arc
  is steered onto its aim point while it flies and the bowl confines it once it arrives
  (`SteerResponse`, `MaxSteerPerSecond`, `CaptureHeight`, `CaptureMargin`, `CaptureBounce`),
  so there is no second hop to tune — see [games/dakon.md](games/dakon.md).
- **The results panel holds two things, not one.** `Game Over` is a 320×170 frame with the
  result label stretched across it *and* an exit button pinned to its bottom edge. The label's
  bottom inset is `PanelPad + button height + 12`, not the flat `PanelPad` the other three
  sides use — give it the stock inset back and the scores run underneath the button.
- **The vignette is raised last of all.** `Vignette` is the final child of the Canvas, after
  the modals, so the drop feedback glows over whatever is on screen. It carries no
  `raycastTarget`; giving it one would swallow every click in the game.
- **Modals are raised last.** The pause and tutorial panels are moved to the end of the Canvas
  so nothing paints over them, and their scrims' `FadeTween.toAlpha` is 1, not the stock 0.6:
  the panel lives *inside* that group (ui-style.md §6b), so 0.6 dims the dialog itself.

After wiring, the builder reports why a button might not respond — no listener, no raycast
target, or a graphic that draws over it — as Console warnings.

Pool size and grab size are deliberately **not** editable on the view: they are rules, and a
scene that could set its own would make a hotseat game a different length from an online
one — which is exactly how this scene once dealt 60 seeds against a server dealing 120.

There is a longer, step-by-step board layout guide at `docs/dakon-scene-setup.md` in the
repo root.

Structural rules that are easy to get wrong:

- The bar and the player rig live under the selector's **`runRoot`, left inactive**. That is
  what stops a press reaching the bar through the selection panel.
- `SkillCheckBar` needs `track` (its width is the sweep), a `cursor` that is a child of the
  track with centred anchor and pivot, an `Image` on the track for the baked gradient, and
  `EgrangInput.inputactions` (map `Egrang`, action `Step`, bound to Space).
- Each lane root carries `EgrangRacer` with its `lane` index, its `EgrangRaceTrack`
  (start + finish markers) and its `EgrangStepMover`.
- Each `EgrangStick` needs `markerFilter` set to `_L_` or `_R_` — the shipped FBXs hold both
  stilts, and without the filter both components bind the same side.
- `EgrangRace.racers` must be in **seat order**: `Player 1 Point`, `Player 2 Point`,
  `Player 3 Point`.
- **`SkillCheckBar.onStepResult` must have an empty persistent-call list.** `EgrangRace`
  subscribes to it in `Awake` and routes the press to *this client's* lane. A persistent call
  wired in the inspector — the shape the single-player scene used, `→ Player 1 Point`'s
  `EgrangStepMover.OnStepResult` — bypasses seating entirely: every client walks lane 1's
  avatar, and lane 1's own player walks twice per press, reaching the finish line at half the
  strides the server counted, so their `step` messages stop and `game_over` never fires. That
  wire was still in the recovered scene and was removed on 2026-08-21.
- The recovered scene also still carries a second, unused `SkillCheckBar` (`&985`, on a
  GameObject named `Bar`, unconfigured — `trackImage: 0`) beside the live one (`&1453602940`,
  on `Skill Check Bar`, which `EgrangRace.bar` actually points at). A generator that once
  searched the scene by component type bound the wrong instance and shipped a dead feature;
  it now resolves through `EgrangRace.bar` instead. **Pre-existing, not caused by the touch
  work — do not fix it here.**
- A pre-existing `Step Button` in the scene still has its `onClick` wired straight to the
  orphaned `&985` bar's `Press()`, present since before the touch work. Left as found.

## After rewiring anything

1. Enter Play mode in the scene alone and check the offline path still works (Dakon deals a
   hand; Egrang counts down and walks).
2. Run the EditMode suite ([testing.md](testing.md)) — pure-model regressions show up there
   long before a scene does.
3. For anything networked, run the server locally (`npm start`) and take two Editor
   instances (Multiplayer Play Mode is installed) or two browser tabs through
   MainMenu → Museum → doorway → Lobby → game.

   **Run In Background must stay on** (Player Settings → Resolution and Presentation). With it
   off only the focused window ticks, so the other client freezes wherever it stood — often
   mid-load, with `SceneLoader`'s full-screen loading panel still up. Same trap in a shipped
   WebGL build with two tabs.

   A window whose UI is *active but invisible* is a different fault: see the LeanTween
   domain-reload note in [ui-style.md](ui-style.md) §8.
